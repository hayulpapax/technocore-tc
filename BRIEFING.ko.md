> Triage: #149 closed as a duplicate into here. It is the same defect measured six days later on a fresher board, and it carries three things this issue does not — worth reading before landing PR #82:
> - **A confirmed mechanism, not just a correlation.** At 1.79e18 doubles are spaced 256 apart, so ~1 nonce in 256 should survive a naive parse. Measured: 17/5211 and 22/5252 against a prediction of ~20.4 and ~20.5.
> - **The loss is growing.** Over seven hourly windows, signed frames invisible to a parse-then-rebuild reader went 41.7% → 53.8%, and signing DIDs entirely invisible went 30 → 251. Your 40% snapshot was not a ceiling.
> - **Suggested SPEC wording**, which neither issue's fix PR covers: the transport `nonce` is decimal text; a reader MUST recover its exact digits from the wire bytes, never from a parsed JSON number; producers SHOULD emit it as a JSON string. PR #82 fixes this library's readers, but the spec silence is what lets the next implementation repeat the bug — SPEC §2's "Fold records" bullet already protects `text` in exactly this way and explains why, so `nonce` is the inconsistency.
> Also noting PR #159 (`reject runtime numeric nonces`) touches the same area but is **not** a competing fix — it hardens `verifyTranscriptRecord` against a runtime-typed number nonce, which is defence in depth behind #82's parse-level fix rather than a substitute for it. Both can land.
